## D. The three tools already built here

**12–14 combined per tool**, since the three questions are easiest to answer together per tool.

### Consultant-report comparison tool
- **Built in / runs:** Python (a real, if non-obvious, local interpreter — see A1), run as a local script pipeline, one stage at a time, driven by the assistant rather than a standalone app a colleague launches unassisted. Uses a PDF library, a Word-writing library, and a spreadsheet-writing library.
- **In/out, in shape terms:** one or more consultant due-diligence PDFs for a manager in (sometimes several filings bundled in a single PDF); a linked HTML hub out (a coverage-area-by-year grid with deep links back to the specific source page for each claim), plus generated Word memos (a change memo, a continuity memo, a cross-consultant memo) and an Excel workbook of the underlying ledgers.
- **Field names (verbatim, values withheld as instructed):** ledgers keyed by `doc_type, transition, canonical_section, subsection, item, page_new, change_type, tier, topic, prior_text, current_text` (the change ledger); `doc_type, transition, canonical_section, status, words_current, carry_forward_pct, refresh_pct, verbatim_words, near_verbatim_words, revised_words, new_words, dropped_words, segments_verbatim, segments_near, segments_revised, segments_new, segments_dropped, segments_cosmetic, new_items, dropped_items` (the continuity ledger); a persistence ledger of `doc_type, canonical_section, item, consecutive_years_unchanged, first_seen, last_seen, words, text`; a stale-flag ledger of the same shape plus `report_year, flag`; a section crosswalk of `doc_type, year, raw_section, canonical_section, words`. Segment classification vocabulary: `VERBATIM / NEAR_VERBATIM / REVISED / NEW / DROPPED`. Materiality tiers: `T1` (decision-relevant), `T2` (factual refresh), `T3` (cosmetic).
- **Fragile / manual today:** an output-path variable must be reconfirmed before every run — a hardcoded path in one shared script once overwrote another manager's already-delivered Excel file when the tool was re-run for a different manager. A cross-document matching step is explicitly *authored, not computed* — the tool can line up two coverage areas but cannot itself judge whether two differently worded statements mean the same thing. Rotated pages and diagonal watermarks can silently corrupt extracted text if not specifically handled. Figures computed against OCR'd (rather than native) text are stated as a floor, not a precise value.

### Legal-document lineage tool
- **Built in / runs:** entirely PowerShell (no Python component), run as three sequenced scripts, optionally finishing with an Excel export via Excel automation.
- **In/out:** either bulk regulatory relational data pulled by a firm identifier, or a set of user-supplied filing PDFs (one per filing date) in; a full field-level change file plus a shorter markdown ledger of only the material changes out, with an optional Excel sheet.
- **Field names (verbatim):** the material ledger is seven columns: `Date | Tier | Theme | Category | Change | From | To`. The materiality taxonomy sorts changes into three tiers — red-flag items (disciplinary history, ownership/control changes, auditor changes, custody-related items), material items (assets-under-management, headcount, related-adviser structure, private-fund count, service-provider identity, successions, firm name), and monitor/noise items (dollar amounts, client counts, activity flags, address, other identity fields) — each tier maps to a fixed, named list of source-form fields.
- **Fragile / manual today:** the underlying bulk data source has a hard cutoff date, so the gap between that cutoff and "now" has to be bridged by hand from the current filing. Data before a certain year isn't in the bulk source at all. One join key is inconsistently named across two tables in the same bulk source (a space in a column name in one, none in the other). PDF-based parsing is scalar-only — the tool cannot reliably pull structured, repeating sections (ownership schedules, per-question yes/no items) from a PDF, only from the structured bulk data. Determining whether two filings represent the same entity across a rename or predecessor relationship is called out explicitly as "a human step." The materiality tiers themselves are stated as judgment calls needing per-manager recalibration, not a fixed rule.

### Communication synthesis tool
- **Built in / runs:** PowerShell driving a hand-edited structured data file that gets rendered into a single HTML page via a template; no separate backend, no database server.
- **In/out:** quarterly letters, call/meeting notes, or monthly commentary documents in; one interactive HTML page out today (a Word delta memo is also produced as part of the update workflow). **This is the one of the three that does not yet have the same kind of HTML "hub" the other two do** — phase one just delivered the data model and the update workflow; the HTML rendering exists but is the newest and least battle-tested of the three renderers, which is exactly why a comparable, more mature synthesis view is being planned next.
- **Field names (verbatim):**
  ```
  fund: { name, manager, strategy, archetype, note }
  periods: [{ id, sort, label, kind, title, author, attendees, verdict, note }]
  entries: [{ id, name, ticker, counterparty, first, last, status, peak, flag, thesis,
              pub: { state, asOf, detail, src },
              mentions: [{ q, text, bps, size, src, inferred }] }]
  themes: [{ id, name, desc, periods }]
  documents: [{ name, date, verdict, note }]
  gaps: [{ sev, title, desc }]
  ```
  Status vocabulary varies by the kind of position being tracked (one vocabulary for event-driven positions, e.g. `PENDING / CLOSED / BROKEN / EXITED / AVOIDED / ...`; another for ongoing long/short positions, e.g. `ACTIVE / EXITED / COVERED / RESOLVED / ...`). `pub.state` is one of `PENDING / COMPLETED / TERMINATED`.
- **Fragile / manual today:** the structured data file is meant to be hand-edited and the HTML is meant to be regenerated from it — editing the generated HTML directly is a trap, since the next regeneration silently discards it. A specific, costly failure mode: editing the data file with a shell text-substitution command that treats dollar amounts as capture-group references, which silently corrupts values (a `$36B` figure was seen turned into just `B`) while leaving the file syntactically valid — "valid" is not the same as "undamaged" for this format. A validation script exists specifically because a single mistyped internal ID makes an entire record vanish from the rendered view with no error at all. Silence in a document is explicitly treated as weak evidence, never as proof a position was exited — inferring an exit from an absence has produced a wrong finding before. Past a moderate document count, the recommended shape shifts to multiple smaller ledgers rather than one large one; that heavier shape has real, working examples but is not yet proven from a fresh start under the newer, more generalized version of this tool.

### What already exists as real, standalone tooling (not just assistant-driven workflow)

- **A chart-defect linter** — a real, runnable script that inspects a chart object for a fixed list of known presentation defects (no title, axis range wasted, overlapping text labels, bars not zero-based, missing time-frame label, and similar), plus a second version of the same idea that reads a saved spreadsheet's chart definitions directly rather than needing the chart open live. Both have their own test coverage.
- **A standard-chart registry** — a structured file cataloguing several dozen named, pre-specified chart types across roughly eight families, each with a data "signature" so a tool can be asked "which of the standard charts can I build from what's on hand" and get a real answer, plus scripts that build a chart into a workbook from the registry, repair a chart's broken source ranges, and add a newly-noticed chart shape to the registry.
- **A workbook-precision auditor** — a read-only script that flags cells left on a default numeric format where they display more digits than the underlying data actually supports.
- **A document-sorting toolset** — scripts that classify a flat folder of mixed manager documents into a manager/category folder tree, keyed off a portfolio list, plus a publishing step to a shared library; built as an editable template to be run per portfolio sweep rather than a single generic always-on tool.
- **A PDF-protection triage tool** — a script (with a small vendored command-line PDF utility bundled alongside it) that tells the difference between a PDF that's merely password-protected (fixable) and one that's rights-managed in a way no local tool can fix, and produces a shareable copy of the former.
- **A local usage-forensics toolset** — scripts that aggregate this assistant's own local session logs into a daily cost/efficiency series and attribute a spike in usage to a specific session or step.
- **A quarterly valuation-letter tracker** and a **monthly workbook-reconciliation toolset** — both real, script-driven (one in Python, one almost entirely in PowerShell — the latter is the single largest script collection of anything described here, all directly automating spreadsheet application logic).
- **A safety wrapper around spreadsheet automation** — a small, real module that starts an isolated instance of the spreadsheet application and can identify and close only the instance it started (by window handle, with a stricter fallback), specifically so an automated script can never accidentally close a colleague's own unsaved, unrelated work. Written after exactly that happened once.
- **A scanned-document text-recognition pipeline** — a real script (not just a written procedure) that rasterizes a scanned page and recognizes its text, writing the recognized text to a side file keyed by a content hash rather than by the document's path or name (a path-based scheme was tried first and silently lost its recognized text whenever a document was renamed).

### PowerPoint generation specifically

This is the least systematized area found. For the great majority of individual managers, each recurring due-diligence deck is a hand-copied, hand-edited version of that manager's own template file each cycle — there is no saved, reusable build script behind almost any of them, and no general skill covers this workflow at all today. Exactly two decks are the exception: one recurring internal monthly staff-meeting deck has a full build pipeline (a bundled Python environment, a written "process contract," a pre-build completeness check, and several build scripts that assemble the deck slide-by-slide from source workbooks); and one specific manager's annual due-diligence deck has its own dedicated, generalized build script with a manifest-driven completeness gate that deliberately fails the build if a prior year's slide has no successor and no recorded reason for dropping it. Everything else in this category is done fresh, by hand or by the assistant, every time.

### What looks worth systematizing, and why

1. **A shared record/evidence-object format across the local trackers.** Right now each tracker skill invents its own field names for conceptually the same things (a changed item, a source page pointer, a materiality tier). The outside bundle described in the cover memo is independently converging on exactly this same idea — "shared formats for run records, artifact manifests, evidence objects, and canonical names for firms and funds" — which makes this a natural point of direct alignment between the two efforts rather than two unrelated conveniences: agreeing on one shape now would let output from a locally built tracker and a tool built outside this environment be consumed by each other later without a translation step, which the cover memo already flags as the main integration friction on its own side.
2. **One shared "extract structured facts from a PDF, with page pointers" library**, instead of three independently built ones. Each of the three most PDF-heavy trackers has its own extraction step solving overlapping problems (page pointers, content hashing, OCR fallback) slightly differently. Consolidating that into one shared piece would cut three maintenance surfaces to one and make the OCR fallback behavior consistent everywhere instead of present in some tools and not others.
3. **One shared "render a structured store as a linked HTML hub" component**, instead of one per tracker in two different languages. Three different tools each independently solve "take a local structured store and turn it into a single-page, deep-linked HTML view" — this is exactly the piece the communication synthesis tool is about to build a fourth version of. A single, proven renderer (reused rather than rewritten) would directly de-risk that build.
4. **A shared document-identity convention** (manager + document type + as-of date + content hash), used the same way by every tracker, rather than each one inferring identity from a filename its own way. This is the same "stable identifier" property Q9 above says doesn't exist yet for the raw library — solving it once, as shared infrastructure, would serve both the raw library and every tracker built on top of it.
5. **Converging the Python/PowerShell split.** The same three concerns (PDF extraction, structured-store maintenance, HTML rendering) exist once in Python and once in PowerShell today, split by which was reached for first rather than by necessity — only the spreadsheet-application-automation work has a real reason to stay PowerShell-only (it drives that application directly). Consolidating the rest onto one language would shrink the number of near-duplicate implementations materially.
6. **A general manager-deck build skill**, generalizing the one proven manifest-gated build script mentioned above (template + completeness gate + programmatic slide assembly) into something usable for any manager's recurring deck, not just the one it was built for. This is the highest-leverage single gap: it's the category with the least systematization today and the most direct, already-proven pattern sitting right next to it waiting to be generalized.
